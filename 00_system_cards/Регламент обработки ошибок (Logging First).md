# Регламент обработки ошибок (Logging First)

## 1. Принцип Logging First
Любое устранение сбоя начинается с фиксации инцидента. Никакие правки кода или конфигурации не применяются до момента документирования проблемы.

## 2. Разделение суточных потоков
* **`Вахтенный_журнал/Инциденты YYYY-MM-DD.md`** — закрытый системный журнал инцидентов. Ведется исключительно автоматикой и ассистентом при фиксации сбоев. Ручное редактирование пользователем исключено.
* **`Входящие/Дневник YYYY-MM-DD.md`** — открытый дневной файл пользователя. Предназначен исключительно для ручных оперативных заметок, мыслей и наблюдений в течение дня.

## 3. Обязательная структура записи инцидента
Каждая запись в журнале инцидентов содержит:
1. **Время:** Точная отметка в формате `YYYY-MM-DD HH:MM`.
2. **Компонент:** Скрипт, утилита или файл конфигурации.
3. **Симптом:** Точное поведение системы, вывод терминала или код ошибки.
4. **Причина:** Анализ корня проблемы.
5. **Действия:** Пошаговые операции по устранению с обязательной проверкой результата.

## 4. Звуковая индикация сбоев
* Системный звук ошибки: `/System/Library/Sounds/Basso.aiff` или `/System/Library/Sounds/Glass.aiff`.
* Системный звук успешного восстановления: `/System/Library/Sounds/Pop.aiff`.

## 5. Барьер синхронизации с удалённым репозиторием (Remote Guard)
Работа над устранением сбоя или закрытием задачи не считается завершённой до верификации внешнего контура:
1. Обязательный `git push` после фиксации коммита с решением.
2. Проверка статуса командой `git status`.
3. Стоп-линия: обязательное наличие строки `Your branch is up to date with 'origin/main'`.
4. При статусах `ahead` (не отправлено), `behind` (рассинхрон) или ошибках сетевого подключения (`fatal`, `exit code 128`) движение дальше блокируется до полного восстановления паритета с сервером.
