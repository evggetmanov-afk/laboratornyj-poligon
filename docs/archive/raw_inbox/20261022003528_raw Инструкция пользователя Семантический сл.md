Инструкция пользователя: Семантический слой и тезаурус

Настоящее руководство описывает правила и сценарии работы с семантическим слоем «Лабораторного полигона» и проекта «Tennis Blitz» в соответствии с архитектурным стандартом ADR-004.

1. Зачем это нужно и как устроено

Семантический слой решает три задачи:

Устранение терминологической путаницы: нормализация разговорных синонимов, сленга и технических жаргонизмов в канонические понятия ядра.

Разделение физики и фасада: сохранение честной физической сущности (биомеханика, файловые операции) при одновременной генерации понятных клиентских отчетов.

Контроль контекста для LLM: передача в языковые модели строгих дефиниций с инвариантами («Чем сущность НЕ является») для предотвращения смыслового дрейфа и галлюцинаций.

Базовые принципы

Атомарность: каждое понятие живет в отдельном файле в docs/thesaurus/LEX-XXX_<name>.md.

Единая витрина: файл docs/thesaurus.md предназначен только для чтения и формируется автоматически.

Двухфазность (On-Demand): сканирование и семантизация запускаются по требованию оператора для готовых документов. Конвейер быстрого сохранения файлов (inbox) работает без участия семантических скриптов.

2. Структура словарной карточки

Все новые карточки создаются строго на основе эталона docs/thesaurus/TEMPLATE.md.

Пример карточки:

---
id: LEX-010
term: Монолитный блок
domain: tennis_mechanics
aliases:
  - rigid_wall_block
  - жесткий блок
  - прием от забора
presentation_mapping:
  client_label: "Глубокий нейтральный блок"
  public_comment: "Плотный прием по месту, удержание глубины против мощной подачи"
broader: []
narrower: []
status: approved
---

### Физика среды (Честная суть)
Распор в ногах, монолитная рама «кисть-предплечье», блокировка струнной поверхности без встречного разгона ракетки.

### Инварианты (Чем сущность НЕ является)
- **НЕ является:** ударом с проводкой (Drive Return).
- **НЕ является:** пассивной подставкой без опоры в ногах (Float Return).

### Слой презентации (Клиентский фасад)
В отчетных материалах трактуется как: *«Надежный плотный прием в глубину корта, нейтрализующий преимущество первой подачи соперника»*.


Поля метаданных (YAML Frontmatter):

id — уникальный идентификатор (LEX-001 — системные, LEX-010+ — предметные).

term — главное каноническое название.

domain — область знаний (system, tennis_mechanics, workflow).

aliases — список синонимов, жаргонизмов и альтернативных вариантов написания.

presentation_mapping — формулировки для внешних клиентов и родителей.

status — жизненный цикл: draft (черновик в _staging/), approved (утверждено в ядре).

3. Инструменты и типовые сценарии работы

Сценарий А: Проверка готового документа (ADR, спецификация, отчет)

Перед закрытием задачи или фиксацией спецификации выполните проверку документа на предмет терминологической согласованности:

Запуск через терминал:

python3 scripts/lexicon_cli.py docs/decisions/ADR-004_Lexicon_and_Thesaurus_Engine.md


Запуск через обертку быстрого вызова:

bash scripts/scan_lexicon.sh path/to/document.md


Примечание: если запустить bash scripts/scan_lexicon.sh без параметров, скрипт автоматически проверит файл, путь к которому скопирован в буфер обмена macOS, либо последний измененный .md документ в docs/ или specs/.

Запуск через Raycast:

Откройте Raycast (Cmd + Space / назначенная комбинация).

Введите команду Ревизия семантики документа.

Просмотрите результат аудита в окне Raycast.

Что показывает отчет:

Точные термины ядра: список понятий, которые уже зафиксированы и используются корректно.

Обнаруженные синонимы: места, где автор использовал сленг («жесткий блок»), и канонический узел тезауруса, к которому он относится ([LEX-010] Монолитный блок).

Кандидаты на регистрацию: неразрешенные ссылки [[...]], которых еще нет в словаре.

Сценарий Б: Добавление нового термина

Скопируйте шаблон:

cp docs/thesaurus/TEMPLATE.md docs/thesaurus/_staging/LEX-XXX_new_term.md


Заполните карточку:

Укажите честную физику среды.

Обязательно заполните блок «НЕ является» (минимум 1-2 пункта).

Задайте клиентский фасад (client_label).

При согласовании оператором:

Переведите статус в status: approved.

Переместите файл из _staging/ в docs/thesaurus/.

Добавьте строку в сводную таблицу docs/thesaurus.md.

Сценарий В: Передача онтологии в новую LLM-сессию

При старте новой сессии с языковой моделью для исключения смыслового дрейфа сгенерируйте компактный онтологический блок:

python3 scripts/lexicon_cli.py --dump-llm | pbcopy


Срез в формате <system_ontology> будет скопирован в буфер обмена. Вставьте его первым сообщением в чат вместе с задачей.

4. Памятка ролей

Оператор: запускает скрипты, перемещает файлы по инструкции, принимает решение о переводе карточки из draft в approved.

Мастер (скрипт / LLM): сканирует тексты, подсвечивает синонимы и готовит черновики карточек. Не имеет права менять канонические файлы ядра без ведома оператора.

Архитектор: определяет схемы данных, форматы карточек и вносит изменения через процедуру ADR.
