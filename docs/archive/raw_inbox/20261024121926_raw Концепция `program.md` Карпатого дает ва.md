Концепция `program.md` Карпатого дает вам сразу несколько готовых инженерных шаблонов, которые ложатся на архитектуру автономных и полуавтономных пайплайнов:

---

### 1. Архитектурное разделение: «Неизменяемый арбитр» против «Полигона»

В паттерне Карпатого ключевое звено — жесткое разделение прав:

* `prepare.py` неизменяем (это эталон, правила игры, инвариант).
* `train.py` мутирует (это рабочая область агента).

**Практическая польза:**
Когда вы ставите LLM задачу оптимизировать код, генерировать разметку или рефакторить алгоритм, нельзя давать модели доступ к коду проверки и тестам. Модель всегда стремится упростить себе жизнь (закон Гудхарта): закомментировать сложные проверки, изменить критерий ошибки или захардкодить выход. Паттерн Карпатого показывает стандарт: изолировать проверочный контур в read-only слой, давая LLM на запись только целевой скрипт.

---

### 2. Принцип «Параллельный механизм / Чистый откат» вместо порчи рабочего кода

Инженерный инстинкт Карпатого в `program.md` решает проблему деградации скриптов:

* Если гипотеза ухудшила результат — немедленный `git checkout <file>`. Никаких накоплений мусора и попыток судорожно починить сломанное поверх старого.
* Если гипотеза подтвердилась — атомарный `git commit` с фиксацией дельты метрики.

**Практическая польза:**
Это решает проблему «галлюцинаторного дрейфа» в длинных сессиях генерации кода. Вы можете заставить локального агента (или скрипт-оркестратор) работать не с базовым файлом напрямую, а через временную ветку / параллельный файл-кандидат, автоматически сбрасывая состояние до исходного, если тестовый прогон завершился неудачей.

---

### 3. Markdown как детерминированный конечный автомат (FSM)

Вместо написания громоздких систем на Python с десятком классов для управления состоянием агента, `program.md` использует обычный структурированный текст.

**Практическая польза:**

* **Минимум сущностей:** Markdown задает строгую машину состояний: `Гипотеза -> Запуск -> Парсинг run.log -> Ветвление (A или B) -> Лог в TSV`.
* **Устранение диалоговой энтропии:** В контракте прямо прописан запрет на вежливые паузы и переспрашивания («Человек спит, не спрашивай разрешения, крути цикл»). Это переводит взаимодействие с LLM из режима «чат-собеседник» в режим «детерминированный фоновый демон».

---

### 4. Внешний TSV-лог вместо контекстной памяти модели

Карпатый сознательно не полагается на память контекстного окна LLM для отслеживания истории попыток. Он обязывает модель вести плоский файл `results.tsv`:

* Прочитал последние строки `results.tsv` $\to$ понял, что уже тестировалось $\to$ выдвинул новую гипотезу $\to$ дозаписал результат.

**Практическая польза:**
Контекст LLM не засоряется простынями логов неудачных попыток. Даже если сессия агента перезапустится или контекстное окно сбросится, файл `results.tsv` остается физическим якорем на диске, позволяя продолжить итерационный цикл без потери контекста предыдущих ошибок.

---

### Где это применимо на практике:

* **Автономная оптимизация алгоритмов:** Натравливание локальной модели на отдельный скрипт обработки данных (например, парсер, модуль кадрирования или расчет геометрии) с автоматическим запуском тестов и откатом неудачных вариантов.
* **Калибровка эвристик:** Подбор пороговых значений или весов классификатора в автономном цикле, где метрика качества жестко зафиксирована в эталонном модуле.
* **Регламенты для рабочих директорий:** Размещение аналогичного `.md`-контракта в корне проекта, чтобы любой подключаемый агент (через API или CLI) сразу понимал свои границы прав: что читать, что менять и по какой метрике оценивать «Done».
