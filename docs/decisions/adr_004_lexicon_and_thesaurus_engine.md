# ADR-004: Семантический слой системы (Словарь, Тезаурус и Агент-линковщик)

- **Статус:** Принято (Approved)
- **Контекст:** Лабораторный полигон / Tennis Blitz
- **Дата:** 2026-10-21

## 1. Зачем это нужно (Суть проблемы)
В системе зафиксированы две проблемы:
1. **Каша в словах:** Одну и ту же сущность модель и оператор называют разными словами (исходник, черновик, видос, сброс). Из-за этого скрипты и LLM-агенты дают сбои и сбивают классификацию.
2. **Два несовместимых мира:**
   - Практическая работа тренера и аналитика опирается на честную физику и биомеханику (кисть провернуло, опора ушла, жесткий блок).
   - Клиенты, родители и спортивные отчеты требуют штампов и обтекаемых терминов (невынужденная ошибка, глубокий прием, активная игра).

Смешивать их нельзя: это ведет к потере сути на корте. Игнорировать фасад тоже нельзя: отчет должен быть понятен заказчику. Решение — жесткая таблица перевода физики среды в клиентский фасад.

## 2. Архитектурное решение: Атомарные карточки
Отказываемся от ведения единого монолитного файла-словаря для записи.
- Монолитный файл создает риски конфликтов слияния в Git, ломает граф связей в Obsidian (эффект «звезды») и усложняет парсинг скриптами.
- Каждое каноническое понятие живет как отдельный атомарный файл в папке `docs/thesaurus/`.
- Файл `docs/thesaurus.md` в корне документации выступает исключительно как витрина только для чтения (компилируется скриптом или собирается через Dataview).

## 3. Двухфазная схема работы (Точки триггера)
Запрещено встраивать языковые модели и семантический разбор в конвейер быстрого сохранения файлов.
1. **Фаза 1: Быстрый инжест (Скрипты)**
   - Сброс из буфера, раскладка файлов через утилиты приема.
   - LLM и внешние API сюда не допускаются. Среда работает без сетевых задержек.
2. **Фаза 2: Семантическая фиксация (По требованию)**
   - Запускается вручную оператором (горячая клавиша / CLI) только для готовых документов: спецификаций, отчетов матчей, ADR.
   - Скрипт-ревизор сканирует текст, сравнивает термины с `docs/thesaurus/` и выдает в терминал отчет:
     - обнаружен синоним — предложить добавить в `aliases` существующей карточки;
     - обнаружено новое устойчивое понятие — предложить сформировать черновик в `docs/thesaurus/_staging/`.
   - Любая запись выполняется только после подтверждения оператором.

## 4. Разграничение ответственности
- **Агент (Секретарь и ревизор):** находит синонимы, готовит черновики карточек (`status: draft`), проверяет граф на битые ссылки и собирает выжимку словаря для системных промптов.
- **Человек (Оператор и Архитектор):** обладает правом вето, переводит карточки в канон (`status: approved`), разрешает смысловые коллизии.

## 5. Таблица перевода системных понятий (Шлюз терминов)

| Как называют в жизни | Канонический термин | Физический смысл |
|---|---|---|
| Исходник, черновик, домашка, видос, текст от клиента, сброс | **Сырьё (raw)** | Необработанный материал в буфере входящих. В работу исполнителю не отдавать. |
| Заявка, тикет, промпт, таска, ТЗ, бриф | **Карточка задания (InCard)** | Проверенный контракт: что взять, что сделать, критерий готовности. |
| Исполнитель, нейронка, аналитик, скрипт, работяга | **Мастер (Master)** | Изолированный исполнитель, решающий задачу по жесткому контракту. |
| Тест, проба, полигон, ветка | **Песочница (Sandbox)** | Изолированная область для тестов без риска повредить ядро. |
| Готовый файл, финалка, релиз, отчет | **Готовая продукция (ReadyOut)** | Чистовой результат, готовый к выдаче в Obsidian или архив. |

### Запрет на недифференцированное слово «Управление»:
- **Оператор шлюза:** выполняет действия по регламенту и перемещает файлы (решений не принимает).
- **Мастер:** анализирует материал, нарезает клипы, считает механику (управляет объектом задачи).
- **Управленец / Архитектор:** формулирует и меняет правила, топологию и ADR (не трогает руками рабочие файлы задач).
