# Инструкция оператора: Браузерный шлюз и пакетный контейнер CONTAINER

## 1. НАЗНАЧЕНИЕ И БАЗОВАЯ ИДЕЯ
Браузерный шлюз — это инструмент атомарной доставки группы связанных файлов из диалогового окна нейросети в локальную файловую систему полигона через системный буфер обмена macOS[cite: 1].

Инструмент решает задачу безопасного переноса сложных узлов (скрипт + тесты + конфигурация + документация) за один шаг, исключая рутинное поштучное копирование и защищая систему от частичной записи (когда часть файлов записалась, а часть потерялась)[cite: 1].

---

## 2. КРИТЕРИИ ВЫБОРА: СКАЛЬПЕЛЬ ИЛИ КОНТЕЙНЕР

| Ситуация | Метод переноса | Формат в чате | Команда оператора |
|---|---|---|---|
| Один файл ($N = 1$): правка бага, отдельная заметка, черновик | Одиночное сохранение (`save`) | Блок с маркером `### FILE:`[cite: 1] | «делай», «пиши код»[cite: 1] |
| Связный узел ($N \geq 2$): новый скрипт с тестами, пачка документации, модуль | Пакетный контейнер (`CONTAINER`) | Контейнер `=== START_CONTAINER ===` | «выгружай пакетом», «контейнер» |

---

## 3. ШЛЮЗОВОЙ ЗАПРОС ФОРМАТА (PRE-FLIGHT GATE)
Чтобы исключить несанкционированную выгрузку тяжелых пакетов, в системе действует регламент ветвления[cite: 1]:

1. Если в рамках задачи подготовлено 2 или более файлов, модель обязана остановить автоматическую выдачу и вывести список файлов[cite: 1].
2. Модель задает вопрос[cite: 1]:
   > *«Подготовлено N файлов. Выгрузить пакетом или по одному через save?»*
3. Оператор выбирает маршрут:
   - Ответ **«выгружай пакетом»** (или **«контейнер»**) -> выдается единый текстовый контейнер `CONTAINER`.
   - Ответ **«по одному»** -> файлы выдаются последовательно отдельными блоками `### FILE:`[cite: 1].

---

## 4. СТРУКТУРА КОНТЕЙНЕРА
Контейнер формируется единым текстовым блоком со строгими маркерами начала и окончания. Внутри передается манифест схемы `poly-container/v1`:

```text
=== START_CONTAINER ===
{
  "schema": "poly-container/v1",
  "task": "Название кванта задачи",
  "files": [
    {
      "path": "относительный/путь/к/файлу_1.py",
      "content": "Текст первого файла...",
      "executable": false
    },
    {
      "path": "относительный/путь/к/файлу_2.md",
      "content": "Текст второго файла...",
      "executable": false
    }
  ]
}
=== END_CONTAINER ===
```

## 5. ПОШАГОВЫЙ РЕГЛАМЕНТ ОПЕРАТОРА

### Шаг 1: Получение и копирование контейнера
После согласования состава файлов и команды «выгружай пакетом» или «контейнер» модель выдает блок контейнера[cite: 1]. Нажмите кнопку копирования блока в интерфейсе чата[cite: 1]. Весь контейнер попадает в системный буфер обмена macOS[cite: 1].

### Шаг 2: Применение на диске
В окне терминала в корне репозитория полигона выполните команду распаковки[cite: 1]:
```zsh
pbpaste | python3 scripts/container_gateway.py
```

### Шаг 3: Проверка транзакции
Скрипт выполняет трехфазную транзакцию (валидация схемы и путей -> запись в буферную директорию `.swap/tx_<timestamp>/` -> атомарный перенос в боевые пути). В терминале отображается отчет по каждому зафиксированному файлу.

### Шаг 4: Контроль рабочего дерева
Проверьте статус Git:
```zsh
git status -s
```
Убедитесь, что все заявленные файлы появились в статусе отслеживания[cite: 1].

## 6. ЗАЩИТНЫЕ БАРЬЕРЫ И ОБРАБОТКА СБОЕВ
- **Принцип All-or-Nothing (Всё или ничего):** если хотя бы один файл манифеста не прошел валидацию или вызвал ошибку записи на этапе подготовки, операция отменяется полностью[cite: 1]. Каталог транзакции стирается, целевые файлы не затрагиваются.
- **Защита системных зон:** запись в `.git/`, `.swap/` и корневые файлы конфигурации запрещена безусловно.
- **Защита ядра:** пути в каталогах `specs/` и `scripts/` блокируются, если не передан специальный флаг `--allow-core`[cite: 1].
- **Защита границ репозитория:** любые попытки выйти выше корня (`../`), абсолютные пути или неразрешенные симлинки вызывают немедленный аварийный останов[cite: 1].
- **Повреждение буфера:** если при копировании текст обрезался или нарушены маркеры `=== START/END_CONTAINER ===`, распаковщик выдаст ошибку и не станет трогать файлы[cite: 1].
