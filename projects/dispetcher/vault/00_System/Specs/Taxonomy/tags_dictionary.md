# Контролируемый словарь таксономии (System Taxonomy Dictionary)

Настоящий документ является нормативным реестром допустимых значений для метаданных YAML frontmatter в хранилище. Использование тегов, типов или статусов вне данного перечня признается ошибкой валидации.

---

## 1. Допустимые значения поля `type` (Тип сущности)

| Значение `type` | Назначение сущности | Канонический каталог размещения |
|---|---|---|
| `manifest` | Верховный конституционный документ | `00_System/` |
| `state` | Оперативный вектор состояния ядра | `00_System/` |
| `registry` | Несгораемый реестр требований/артефактов | `00_System/` |
| `specification` | Нормативные спецификации и схемы | `00_System/Specs/` |
| `adr` | Архитектурное решение | `00_System/Decisions/` |
| `template` | Канонический шаблон заметки | `00_System/Templates/` |
| `runbook` | Инструкция ручного регламента | `00_System/Operations/Runbooks/` |
| `session` | Протокол рабочей вахты оператора | `00_System/Operations/Sessions/` |
| `contract` | Спецификация прав и роли агента | `00_System/Agents/Contracts/` |
| `requirement` | Атомарное требование | `01_Inbox/Baseline_Requirements/` |
| `concept` | Онтологическая сущность базы знаний | `02_Vault/Concepts/` |
| `module` | Описание архитектурного модуля | `02_Vault/Architecture/` |

---

## 2. Допустимые значения поля `status` (Жизненный цикл)

| Значение `status` | Применимость | Семантика |
|---|---|---|
| `inbox` | Требования (`requirement`) | Зафиксировано, ожидает декомпозиции и взятия в работу |
| `in_progress` | Требования, задачи | В активной реализации текущим тактом |
| `done` | Требования, задачи | Реализовано, подтверждено проверкой и коммитом |
| `active` | Спецификации, манифест, state | Действующий системный стандарт |
| `accepted` | Решения (`adr`) | Решение утверждено и вступило в силу |
| `superseded` | Решения (`adr`) | Решение отменено более поздним ADR |
| `stable` | Концепты онтологии | Понятие выверено и не подвержено дрейфу |
| `draft` | Черновики в Staging | Непроверенный материал на этапе валидации |
| `completed` | Протоколы вахты (`session`) | Вахта закрыта с фиксацией точки выхода |

---

## 3. Допустимые значения поля `category` (Категории архитектуры)

- `Core` -- системное ядро, диспетчеризация, базовые правила.
- `Architecture` -- системная архитектура, топология, изоляция сред.
- `Process` -- регламенты взаимодействия, квантование тактов, вахты.
- `Schema` -- стандарты метаданных, таксономия, валидаторы.
- `Security` -- контуры безопасности, права доступа, запреты.
- `Agents` -- интерфейсы, контракты, очереди и буферы агентов.
- `Ingest` -- буферы захвата, конвертация, нормализация входных данных.
- `Operations` -- сессионные логи, чек-листы, ручные прогоны.
- `Templates` -- канонические шаблоны сущностей.
- `Storage` -- физические носители, облачный и локальный контуры.
- `Deployment` -- инкубация, экспорт, версионирование Git.
- `Ontology` -- смысловые сущности предметной области хранилища.

## 4. Контролируемый реестр системных тегов (`tags`)

Все теги пишутся строго в нижнем регистре (lowercase) с использованием символа подчеркивания `_` для составных слов. Использование CamelCase или дефисов в тегах запрещено.

### Системное управление и архитектура
- `system` -- принадлежность к системному контуру `00_System`.
- `architecture` -- архитектурные стандарты и топология.
- `principles` -- основополагающие принципы и аксиомы.
- `governance` -- правила управления и процедурные нормы.
- `isolation` -- физическое разграничение станка и хранилища.
- `adr` -- запись архитектурного решения.
- `core` -- базовые механизмы ядра.

### Процесс и исполнение
- `process` -- правила ведения рабочего процесса.
- `circuit_breaker` -- предохранители от сбоев и перегрузок.
- `engineering` -- инженерные практики и дисциплина.
- `dispatch` -- диспетчеризация и координация шагов.
- `state` -- метки вектора состояния.
- `session` -- протоколы вахт.
- `log` -- журнальные записи.
- `operations` -- операционная деятельность.

### Требования и метаданные
- `requirement` -- атомарные требования к системе.
- `inbox` -- сущности входного потока.
- `registry` -- реестры и сводные списки.
- `schema` -- спецификации форматов данных.
- `yaml` -- стандарты frontmatter-разметки.
- `taxonomy` -- терминологический контроль.
- `linter` -- правила валидации целостности.
- `templates` -- шаблоны заметок.

### Агентный периметр и безопасность
- `agents` -- компоненты взаимодействия с LLM и агентами.
- `queue` -- файловые очереди задач.
- `contracts` -- ролевые контракты агентов.
- `permissions` -- разграничение прав доступа.
- `sandbox` -- изолированные буферы исполнения.
- `staging` -- буферная зона валидации входящих артефактов.
- `security` -- правила информационной безопасности.
- `human_in_the_loop` -- обязательный шлюз ручной проверки человеком.
- `audit` -- процедуры аудита и ревизии.

### Инфраструктура и хранение
- `git` -- практики версионирования.
- `storage` -- параметры физических накопителей.
- `cloud` -- облачные хранилища.
- `hot_cold` -- разделение горячего и холодного контуров.
- `config` -- конфигурационные параметры.
- `portability` -- переносимость без жестких путей.
- `incubator` -- этап инкубации хранилища.
- `deployment` -- процедуры развертывания и миграции.
- `migration` -- отчуждение хранилища в отдельный репозиторий.
- `obsidian` -- специфика среды Obsidian.
- `dataview` -- интеграции со структурированными запросами.
- `ontology` -- смысловая база чистового слоя.
- `concept` -- концептуальные единицы онтологии.

## 5. Системные запреты (Negative Constraints)

1. Запрещено создание свободных тегов ad-hoc без предварительного включения в данный реестр.
2. Запрещено использование синонимов (например: `req` вместо `requirement`, `task` вместо `process`).
3. Запрещено использование кириллицы в значениях `type`, `status`, `category` и `tags`.
4. Запрещено смешение регистров (например: `Core` как тег; тег обязан быть `core`).
