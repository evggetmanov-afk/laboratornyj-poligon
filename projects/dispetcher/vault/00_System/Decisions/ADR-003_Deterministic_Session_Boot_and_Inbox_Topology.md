# ADR-003: Архитектура подсистемы 01_Inbox и детерминированный протокол старта сессий

## 1. Контекст и проблема
1. Стартовый скрипт `start_dispetcher.py` передавал агенту только статические правила, игнорируя динамическое состояние хранилища. При смене чата агент терял контекст («амнезия»), переспрашивал статус и не знал, какую задачу брать следующей.
2. Отсутствовал физический механизм для оператора взять задачу вне общей очереди без переписывания скриптов или передачи CLI-аргументов.
3. Отсутствовала детерминированная модель перемещения сырья от момента поступления до архивации.

## 2. Принятые архитектурные решения

### 2.1. Идентификация (Timestamp UID)
- Отказ от искусственных последовательных счетчиков на входе.
- Идентификатором сырья является **высокоточный штамп времени** (включая сотые доли/миллисекунды): `YYYYMMDDHHMMSSss[_slug].md`.
- Имя файла **иммутабельно**: оно не меняется при перемещении по шлюзам конвейера.

### 2.2. Физическая топология шлюзов `01_Inbox`
Управление статусом задачи осуществляется исключительно через её физическое перемещение между каталогами:
- `01_Inbox/00_Raw/` — первичный приём необработанного сырья.
- `01_Inbox/01_Queue/` — общая очередь упорядоченных задач (FIFO). Сюда попадают только атомарные задачи. Если файл в `00_Raw` композитный, он предварительно нарезается.
- `01_Inbox/02_Priority/` — шлюз ручного внеочередного вмешательства оператора. Если оператор положил сюда файл, система обязана взять его, игнорируя общую очередь.
- `01_Inbox/03_Processing/` — атомарная зона блокировки (Lock). Вмещает строго от 0 до 1 файла. Если здесь лежит файл — система находится в активной незавершенной транзакции.
- `01_Inbox/04_Processed/` — несгораемый архив отработанного сырья.

### 2.3. Алгоритм выбора рабочей цели (State-First Boot)
При запуске нового сеанса или агента проверка директорий выполняется строго в следующем приоритете:
1. `03_Processing/` не пуста? ➔ **Аварийный возврат (Recovery):** завершить зависший такт или вернуть файл в очередь. Новые задачи блокируются.
2. `02_Priority/` не пуста? ➔ **Внеочередной захват:** переместить файл из `02_Priority/` в `03_Processing/`.
3. `01_Queue/` не пуста? ➔ **Штатный захват (FIFO):** переместить первый файл очереди в `03_Processing/`.
4. Везде пусто? ➔ Система находится в режиме ожидания входящих.

### 2.4. Замкнутый цикл закрытия такта
Такт считается завершенным только при атомарном выполнении цепочки:
1. Создан артефакт в `02_Notes/CN-***.md` со ссылкой на исходный Timestamp UID.
2. Сырьевой файл перемещен: `mv 01_Inbox/03_Processing/<UID>.md 01_Inbox/04_Processed/<UID>.md`.
3. В `00_System/INBOX_REGISTRY.md` проставлен чекбокс `[x]`.
4. Сделан коммит в Git.

## 3. Последствия
- Полная ликвидация контекстной амнезии: новый чат считывает физическое состояние диска за 1 шаг.
- Отсутствие логических костылей в CLI: оператор управляет приоритетом простым перемещением файла в папку `02_Priority/`.
