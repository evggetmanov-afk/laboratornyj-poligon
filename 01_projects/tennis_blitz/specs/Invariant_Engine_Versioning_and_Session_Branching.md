# Инвариант: Версионирование ядра и ветвление сессий анализа

## 1. Базовый принцип (Инвариант обратной совместимости)
> Изменение инструментального ядра (скриптов ffmpeg, схем телеметрии, промптов LLM) не должно мутировать или повреждать ранее созданные карточки и зафиксированные результаты анализа.

## 2. Паспортизация данных (Traceability)
Любая сгенерированная карточка инцидента (TEMPLATE_ATOMIC_CARD.md) обязана содержать в метаданных явную версию ядра, которым она была получена:
```yaml
engine_version: 1.0.0
protocol: 4-shot-classic
session_ref: 2026-10_wta_beijing_final
```

## 3. Регламент экспериментов над разобранным матчем (Session Forking)
Если по ходу работы с матчем №1 возникает необходимость изменить правила анализа без утраты базового результата:
1. Заморозка базы: Сессия MATCH_01_v1 переводится в статус FROZEN.
2. Создание ветки: Создается параллельный контейнер MATCH_01_v2_exp.
3. Физическая изоляция (Слой B): Исходное видео в 1_source/ не дублируется, а линкуется (hardlink / symlink). Каталоги 2_scratch/ и 3_artifacts/ создаются заново.
4. Результат: Карточки версии v2 маркируются суффиксом эксперимента или повышенной версией протокола. Базовый срез v1 остается инвариантным.

## 4. Миграция инструментального ядра (Core Evolution)
- Ядро v1.x -> Git Tag: Текущее состояние скриптов и спецификаций фиксируется тегом core-v1.0.0.
- Новое ядро v2.x: Разрабатывается в изолированной ветке или с явным изменением engine_version: 2.0.0.
- Исторические матчи: По умолчанию не перезаписываются (Forward Only). Пересборка старых матчей допускается только через процедуру бенчмарк-сравнения в отдельной сессии.
