# Инвариант: Разделение юрисдикций кода и атомарность записи

## 1. Слой A: Замысел и генезис
* **Слой A1 (Голос):** «Код — питон и баш-скрипты, много нативных документов.»
* **Слой A2 (Телеология):** Ликвидация хаоса выполнения и неконтролируемых побочных эффектов (*side effects*). Обеспечение абсолютной предсказуемости исполнения, защита нативных Markdown-артефактов от деградации, битых состояний, гонок процессов и случайного затирания.

## 2. Слой B: Физика среды и риски энтропии
* **Дисперсия ответственности:** Размытие ролей Bash и Python приводит к созданию ненадёжных монолитов, где парсинг данных и работа с ОС перемешаны.
* **Риск повреждения данных (*In-place Overwrite*):** Прямая запись скриптами поверх боевых файлов (`> target.md`) при сбое оставляет артефакты в пустом или повреждённом состоянии, ломая парсеры YAML Frontmatter и Dataview.
* **Иллюзия атомарности при межфайловых перемещениях:** Использование системного `/tmp` (часто `tmpfs`) для подготовки файлов хранилища приводит к тому, что системный вызов `rename(2)` деградирует до неатомарного `копирование + удаление` между разными точками монтирования.
* **Несброшенный дисковый кэш:** Завершение операции записи без явного сброса буферов ОС грозит потерей данных при внезапном сбое питания или падении ядра.
* **Неконтролируемое состояние:** Смешение временных файлов, системных скриптов и постоянной базы заметок в едином несегрегированном пространстве.

## 3. Слой C: Детерминированный контракт

### 3.1. Разделение юрисдикций инструментов
* **Bash (Клей и транспорт):**
  - **Задачи:** CLI-обёртки, координация вызова утилит, системные проверки, контроль exit-кодов, управление процессами, Git-транспорт.
  - **Обязательный пролог:** Все shell-скрипты обязаны стартовать в строгом режиме:
    ```bash
    set -euo pipefail
    IFS=$'\n\t'
    ```
  - **Ограничение:** Категорически запрещён сложный смысловой парсинг JSON/структурированного текста внутренней логикой shell (строковый regex/sed/awk для логики сущностей).
* **Python (Трансформация и валидация):**
  - **Задачи:** Чистая логика обработки данных, строгая валидация схем Frontmatter, взаимодействие с API/LLM, сборка Markdown/YAML.
  - **Интерфейс:** Предсказуемый ввод/вывод (аргументы CLI или `stdin` $\to$ `stdout`), изоляция виртуального окружения.

### 3.2. Стандарт атомарной записи (Safe Write / Atomic Swap)
* **Запрет слепой перезаписи:** Никакой скрипт не имеет права открывать на запись нативные документы контура напрямую без предварительной сборки во временный буфер.
* **Протокол Atomic Swap:**
  1. **Локализация буфера:** Временный файл создаётся строго на **том же физическом/логическом разделе**, что и целевой документ (в локальной директории `.state/tmp/` или `.swap/` рядом с целевым каталогом).
  2. **Сброс буфера (Flush & fsync):** Запись полезной нагрузки сопровождается обязательным вызовом `flush()` и `os.fsync(fd)` до закрытия дескриптора.
  3. **Валидация целостности:** Проверка буфера валидатором (непустое тело, синтаксическая корректность YAML Frontmatter по схеме).
  4. **Атомарная подмена:** Замещение целевого файла атомарной операцией одной файловой системы (`os.replace` в Python / `mv -T` в GNU coreutils).
  5. **Очистка:** Гарантированное удаление временного файла в блоке `finally`/`trap` при возникновении любой ошибки валидации.

### 3.3. Сегрегация директорий и негативные ограничения (Negative Constraints)
* **`raw/`**: Неизменяемый входящий слепок (сырые логи, дампы, неизменяемый источник правды). Режим: **Read-Only**.
* **`state/`**: Оперативное машиночитаемое состояние, буферы и контракты (включая `.state/tmp/`). Исключается из индекса базы знаний.
* **Постоянное хранилище (`Карточки/`, `Вахтенный_журнал/`)**: Пополняется только детерминированно с соблюдением схемы Frontmatter через процедуру Safe Write.
* **Запреты:**
  - Запрещена запись вспомогательными скриптами в корень репозитория.
  - Запрещено использовать общесистемные пути (`/tmp`, `/var/tmp`) в качестве источника для атомарной замены файлов хранилища.
  - Запрещено модифицировать код скриптов самими скриптами без явного протокола ревизии и версионирования.
