# Спецификация: Диспетчеризация и маршрутизация входящих сущностей (01_inbox -> ready / projects)

## 1. НАЗНАЧЕНИЕ И ОБЛАСТЬ ДЕЙСТВИЯ
Спецификация определяет правила разбора, маршрутизации и перемещения нормализованных документов из входящего накопителя `01_inbox/` в целевые рабочие каталоги:
- `ready/` — готовые карточки базы знаний для импорта в Obsidian;
- `projects/<project_name>/` — контекстные материалы, код и задачи конкретного изолированного проекта;
- `docs/` — пополнение системной документации, стандартов и реестров;
- `_quarantine/` — сущности с невалидной структурой, поврежденным frontmatter или неизвестным назначением.

---

## 2. СИСТЕМНЫЕ ИНВАРИАНТЫ ДИСПЕТЧЕРИЗАЦИИ

### 2.1. Абсолютная неизменяемость сущности (Immutability ID)
- При любом перемещении из `01_inbox/` в целевой каталог **имя файла остается неизменным**.
- Поле `id` в YAML frontmatter не модифицируется и строго тождественно 14-значному префиксу имени файла (`YYYYMMDDHHmmss[_XXX]`).
- Изменение имени файла при диспетчеризации расценивается как нарушение целостности конвейера.

### 2.2. Управление жизненным циклом через поле stage
- При перемещении документа диспетчер обязан синхронно обновить поле `stage` в YAML frontmatter:
  - При переходе в `ready/`: `stage: ready`
  - При переходе в `projects/<name>/`: `stage: project` (или `stage: active`)
  - При изоляции в `_quarantine/`: `stage: quarantine`
- Значения остальных служебных полей (`created`, `type`, `case_id`, `title`) сохраняются без искажений.

---

## 3. ПРАВИЛА МАРШРУТИЗАЦИИ

Маршрутизация выполняется детерминированно на основе классификационных тегов в имени файла и/или полей YAML frontmatter:

### 3.1. Маршрут по тегу домена в имени файла
Шаблон тегов: `[ценность][тип][домен]`
1. **В проекты (`projects/<project_name>/`):**
   - Если тег домена указывает на зарегистрированный проект (например, `[tennis_blitz]`, `[file_saver_lab]`), файл перемещается в `projects/<project_name>/inbox/` или корень проекта.
2. **В системную документацию (`docs/`):**
   - При наличии тега `[docs]`, `[adr]` или `[spec]` документ направляется в соответствующий подкаталог `docs/` (`docs/decisions/`, `docs/manuals/`).
3. **В шлюз чистой базы знаний (`ready/`):**
   - Если тег указывает на общую базу знаний (`[core]`, `[note]`, `[knowledge]`), либо документ является завершенной атомарной карточкой, файл перемещается в `ready/`.

### 3.2. Дефолтный маршрут и изоляция
- Если файл не содержит явных тегов маршрутизации и в frontmatter не указан целевой проект, по умолчанию документ направляется в `ready/`.
- Если у файла нарушена структура YAML frontmatter (отсутствует `id`, поврежден синтаксис, `id` не совпадает с префиксом имени файла), файл немедленно изолируется в `_quarantine/` с сохранением исходного содержимого.

---

## 4. ПРОТОКОЛ ФИЗИЧЕСКОГО ПЕРЕМЕЩЕНИЯ (Write/Move)
1. Чтение исходного файла из `01_inbox/`.
2. Валидация тождественности `id == filename_prefix`.
3. Модификация поля `stage` в оперативной памяти.
4. Атомарная запись во временный файл целевого каталога (`<target_path>.tmp`).
5. Атомарная замена `shutil.move(<tmp>, <target_path>)`.
6. Физическое удаление исходного файла из `01_inbox/`.
7. Логирование операции в консоль: `[DISPATCHED] <filename> -> <target_dir>/<filename>`.
