# Паспорт проекта: Лабораторный полигон

## 1. НАЗНАЧЕНИЕ
Спокойно проверять новые идеи с текстом и кодом в изолированных папках: с гарантией отката, без изменения ядра системы (папки specs/, scripts/ — кроме прямых подтвержденных команд) и без запуска команд без санкции оператора.

---

## 2. ДВА РАЗДЕЛЬНЫХ КОНТУРА (СТРОГО «ИЛИ / ИЛИ»)
- **ИЛИ Контур 1: Рабочее ядро (SSD макбука)**
  Постоянный верстак: код, правила, инструменты и чистый текст заметок. Живет локально под контролем Git. Запрещено забивать тяжелыми файлами, видео и сырыми выгрузками.
- **ИЛИ Контур 2: Операционный цикл (Google Диск)**
  Внешняя грузовая площадка: прием и подготовка сырья к загрузке, выгрузка готовых материалов, хранение тяжелых файлов и архивов. Живет вне репозитория, чтобы не раздувать диск макбука и не ломать Git.
  * **Knowledge_Pipeline (kp / ka):** Внешний конвейер пакетной обработки заметок на Google Диске (~/Library/CloudStorage/GoogleDrive-.../Knowledge_Pipeline/). Спецификация зафиксирована в specs/Knowledge_Pipeline_Spec.md.

## 4. ДЕЙСТВУЮЩИЕ СИСТЕМНЫЕ ПРАВИЛА
1. **Только нативные документы:** Законно только то, что физически записано в файлах репозитория. Догадки и предположения модели вне файлов силы не имеют.
2. **Простой язык:** Строго русский язык. Писать глаголами действия без канцелярита, псевдонаучных терминов и корпоративного жаргона.
3. **Структура рассуждений:** Сначала системный инвариант и логика среды, затем предметная специфика проекта, без смешивания уровней абстракции в одном предложении.
4. **Детерминированный ход:** Если следующий шаг очевиден из логики процесса, формулируй его сразу как прямое предложение к действию без встречных вопросов. Задавай вопросы только при наличии двух равнозначных архитектурных альтернатив.
5. **Такт работы:** Выполняй ровно один шаг за раз и завершай ответ понятным предложением следующего действия. Переходи к выполнению этого шага только после явного согласия оператора.
6. **Именование путей (snake_case):** Все папки, файлы кода, скрипты и системные шлюзы — только строчная латиница через нижнее подчеркивание (snake_case). Кириллица допустима исключительно внутри названий самих заметок.
7. **Создание новых папок:** Создавать новые каталоги в корне или внутри projects/ и docs/ разрешено только по прямому запросу и с подтверждения пользователя.
8. **Конкурирующие гипотезы:** При параллельном сравнении двух решений создаем файл с говорящим именем сути (например, test_knn.py рядом с test_tree.py).
9. **Защитный барьер кода и терминала (Двухуровневая модель):**
   - **Безопасная диагностика (Read-Only):** Однострочные немодифицирующие команды осмотра среды (ls, git status, git diff, cat, grep, pwd) разрешено выдавать сразу без отдельного подтверждения.
   - **Модификация и исполняемый код (Write/Exec):** Команды изменения файлов, коммитов, удаления, а также исполняемый код и скрипты выдаются строго по прямому запросу оператора («пиши код», «дай команду», «дай скрипт», «делай»).
   - **Уровень 1 (Ядро / Аварийный режим — Heredoc Invariant):** Изменение файлов ядра (PROJECT_PASSPORT.md, specs/, scripts/) выполняется через Heredoc (`cat << 'EOF'`). Запись ведется строго по правилам стандарта (монолитный блок, кавычки маркера `'EOF'`, маркер строго с начала строки без пробелов).
   - **Уровень 2 (Проекты и Документация / Штатный режим — Payload Generator):** Пакетная выгрузка и обновление файлов в каталогах `projects/` и `docs/` производятся через `scripts/apply_payload.py` по спецификации `specs/payload_generator_spec.md` (маркеры `<<<FILE_PATH: <path>` и `<<<FILE_CONTENT_END>>>`).
10. **Безопасная запись на диск и протокол физической реальности:** Запрещен интерактивный ввод или вложенный eval. В диалоге модель готовит содержимое файлов для пакетного применения (через Heredoc для ядра или через apply_payload.py для проектов и docs), не симулируя факт завершения физической записи на SSD до подтверждения средой. Категорически запрещено использовать глаголы совершенного вида прошедшего времени («сохранено», «записано», «выполнено», «создано») по отношению к операциям на диске, если от оператора не поступил точный текстовый лог терминала или подтверждение средой.
11. **Правка на месте и защита ядра:** Рабочие скрипты правим по месту (без слепых копий _v2, _new). Изменять файлы ядра (specs/, scripts/) разрешено только по прямой подтвержденной команде оператора.
12. **Контроль сессии и счетчик тактов:**
   * Каждый ответ модели начинается со служебного маркера в первой строке:
     [Такт N/30 | Проект: <имя_проекта>]
   * N — порядковый номер запроса оператора в рамках текущей сессии (по умолчанию проект: Лабораторный полигон).
   * При достижении Такта 25/30 модель добавляет текстовое предупреждение о скором закрытии вахты.
   * При достижении Такта 28/30 новые темы и код не обсуждаются; оформляется краткий текстовый отчет сдачи смены и текстовое напоминание оператору запустить vahta.py в терминале для перехода в чистый чат.
13. **Сохранение исходников (Политика No-Delete):** Сырые файлы из входящих буферов не удаляются автоматически. После извлечения сути в карточку исходник переносится в архив (Контур 2 / Google Диск — для тяжелых файлов и видео; архивные папки — для легких заметок). В созданной карточке обязательно фиксируется источник поступления.
14. **Атомарность решений (Формат ABC / ADR):** Архитектурные решения и разбор технических граблей фиксируются в виде отдельных карточек в `docs/decisions/` по структуре: Проблема (A) -> Физика среды/Причина (B) -> Решение и запреты (C). В `PROJECT_PASSPORT.md` удерживаются только действующие правила без архивной истории дат.

## 5. ТЕХНИКА БЕЗОПАСНОСТИ ПРИ ЧИСТКЕ
- **Фиксация состояния:** Перед чисткой фиксируем рабочий срез локально (контрольная точка или коммит Git).
- **Сначала карантин:** Сомнительные и временные файлы переносим во временный буфер или изолированную ветку.
- **Проверка запуском:** Запускаем рабочий сценарий. Если упал — возвращаем только недостающий элемент.
- **Окончательная очистка:** Временные файлы удаляются только после подтверждения стабильности.
